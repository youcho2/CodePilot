# 会话列表交互 + 未读系统 产品思考

## 解决什么用户问题

1. **操作要两步、还藏着**:改造前处理一个会话(分屏/归档)得先 hover 出三点菜单、点开、再选 —— 高频操作被折叠成「点两下」。
2. **"我不在场时它跑完了"没提示**:CodePilot 支持多会话并行 / 分屏,一个会话在后台跑,用户去看别的会话。回复跑完后回到侧栏,**没有任何标记**告诉他哪个会话有了新进展 —— 用户得逐个点进去看。
3. **归档 ≠ 删除,但用户想要真删**:原本「删除」其实是软删(归档),数据留在库里。有用户明确想**彻底删掉**某些会话。

## 为什么这样设计

### hover 直接给按钮,右键给完整集
高频操作(分屏、归档)hover 就能一键点到,省掉「展开菜单」这一步;低频/破坏性操作(重命名、复制ID、已读、硬删)收进右键菜单,避免 hover 时堆一排按钮显得杂乱。**高频前置、低频后置**是这次交互分层的核心。

### 未读只标记「你不在场时完成的回复」这一个信号
未读系统刻意**不**等同于「有活动」。它只在满足全部条件时点亮:某会话**正在流式的回复结束了** + **它不是你当前看的那个会话**。
- 为什么不是「只要有新消息就未读」:用户自己发的、自己正在看的,不构成「错过」。
- 为什么不是「只要在跑就未读」:跑的过程用的是已有的 streaming 点(转圈),未读要表达的是**完成**这个可回看的结果。
未读回答的是一句很具体的话:**"你去忙别的时候,这个会话替你把活干完了。"**

### 为什么客户端检测,而不是服务端统一判定
流式的生命周期(开始/结束)在**客户端**是直接可观测的(`activeStreamingSessions` 的进出)。服务端要做到同等语义,得额外维护一套「谁在看哪个会话」的在场状态,复杂且易错。于是选择客户端检测 + 一个 DB 列持久化结果。
**代价是诚实标注的**:纯 bridge 后台写入(本端从未观测到 streaming 的会话)不会点亮未读。这是明确写进语义契约的盲区(呼应 CLAUDE.md「反假数据」——宁可少标、不伪造覆盖),而不是用假状态糊过去。

### 为什么标记读/未读不重排序
未读是**状态**,不是**活动**。如果标记未读把会话顶到列表顶部,会打断用户对侧栏位置的空间记忆(「那个会话一直在第三个」)。所以 `updateSessionUnread` 有意不碰 `updated_at` —— 蓝点亮/灭,位置不动。

### 为什么硬删要单独一项 + 强确认
归档(软删)满足绝大多数「让它从列表消失」的需求,且可在 DB 层找回。物理删除是**不可逆的破坏性操作**,所以:① 只放右键、用 destructive 样式;② 独立于归档,不混为一谈;③ 弹强措辞确认框(「永久移除、无法恢复」)。给想真删的用户一条明确的路,同时用摩擦力防误删。

## 已知局限 / 未来方向
- **未读无计数**:目前是布尔蓝点,不显示「几条新回复」。多数场景够用;若并行会话数上去,可能需要数字 badge。
- **bridge 盲区**:见上。若未来要覆盖纯后台写入,需要服务端补一套完成事件来源。
- **不跨设备**:unread 存本地 SQLite,不随账号同步。
- **升级兼容**:新列默认 0,老会话升级后一律「已读」——刻意如此,避免升级瞬间侧栏炸一片蓝点。

# 迭代二:归档即时化 + 项目不该随会话消失

## 解决什么用户问题

1. **归档每次都要确认,拖慢高频操作**:归档是软删(可恢复),但每点一次都弹 confirm。可逆操作配强确认,是把「防误删」的摩擦力用错了地方 —— 用户为了清理列表要一遍遍点「确定」。
2. **项目会话全归档后,项目直接没了(bug)**:用户把一个项目下的会话都归档,想着「先清空,回头再在这个项目里开新会话」,结果整个项目文件夹从侧栏消失了。项目是用户对工作目录的心智锚点,不该因为「暂时没有活跃会话」就蒸发。

## 为什么这样设计

### 可逆的操作就该即时,别用确认框当摩擦力
确认框的价值是给**不可逆**操作加一道刹车。归档可恢复(数据留在 SQLite),弹窗只带来负担不带来安全感。所以三处归档入口(列表 hover、右键、顶栏)统一即时执行;把强确认**只**留给真正不可逆的硬删除。这是一条一般原则:**摩擦力要花在不可逆的地方**。

### 项目的存在,应该锚定「有没有数据」,而不是「有没有活跃会话」
根因是架构上项目从来没有独立身份 —— 它只是「当前可见会话」按目录分组的副产品。可见会话一空,分组就没了,文件夹跟着消失。

修复的思路不是给项目建一张新表(过度设计、要维护同步),而是**把项目的存在重新锚定到 DB 事实**:一个目录只要在库里**还有任意会话**(哪怕全是归档的),它就仍然是一个项目。归档只是把对话藏起来,不该抹掉项目本身。于是空项目文件夹保留下来,继续暴露「+ 新建会话」,用户回头能直接在原项目里接着干。

### 那「怎样才算真正删掉一个项目」——把语义收敛到一个明确出口
一旦「归档全部」不再让项目消失,就必须有另一条路真正移除项目,否则空文件夹会永远堆着。我们把「Remove project」从原来的「归档全部会话」改成**硬删除全部会话**:
- 归档 = 藏对话,项目留着(可逆、日常清理)。
- Remove project = 连项目带对话彻底删掉(不可逆、显式意图)。

这让两个动作语义**互不重叠**:一个管「清理视图」,一个管「销毁数据」。代价是 Remove project 从可恢复变成不可恢复 —— 这是刻意的,并在确认文案里点明「若只想清空列表,归档会保留空文件夹」,把两条路的区别直接摆到用户面前。

### 为什么不用 localStorage 记住项目
另一种实现是客户端在 localStorage 记住「见过的项目目录」。但那样项目身份就漂到了浏览器状态里:换机器 / 清缓存就丢,且和「谁才是真源」割裂。既然 DB 本来就有全部会话(含归档),让项目直接从 DB 派生是**唯一真源**、跨重启稳定、无需额外同步 —— 呼应 CLAUDE.md「每个字段要能追到真实来源」。

## 已知局限 / 未来方向
- **空文件夹会一直留着**:只要还有归档会话,项目就在。若用户归档了大量项目又不 Remove,侧栏可能积累一批空文件夹。目前靠 Remove project 手动清;未来若成困扰,可考虑「隐藏空项目」开关或自动折叠。
- **Remove project 不可逆**:改成硬删后没有回收站。归档仍可逆,但被 Remove 的项目及其对话真删了。是否需要项目级回收站,看用户反馈。
- **排序**:空项目按其最后活动时间(含归档会话)排,自然沉到活跃项目下方 —— 符合「不常用的往下沉」的直觉。
